# OAuth 2.0 & OpenID Connect (OIDC) Educational Lab

Welcome to the Educational OAuth 2.0 and OIDC Lab. This project is built entirely from scratch without using any external Identity Providers (like Auth0 or Keycloak) or heavy libraries like Passport. 
By implementing the protocol manually, you can clearly trace and understand how the different pieces of the OAuth and OpenID Connect specifications work together.

## Quick Start

### 1. Installation
Install all dependencies for the IAM server and the React apps:
```bash
npm install
```

### 2. Start the Applications
Run all three applications simultaneously:
```bash
npm run dev
```

### 3. Ports
- **IAM Server (OAuth/OIDC Provider)**: `http://localhost:3000`
- **Frontend 1 (Public Client 1)**: `http://localhost:3001`
- **Frontend 2 (Public Client 2)**: `http://localhost:3002`

## Concepts Covered

### 1. What is OAuth 2.0?
OAuth 2.0 is an authorization framework that enables applications to obtain limited access to user accounts on an HTTP service. It delegates authentication to the service that hosts the user account and authorizes third-party applications to access the user account.

### 2. What OIDC adds
OpenID Connect (OIDC) is an identity layer on top of the OAuth 2.0 protocol. While OAuth 2.0 is purely for *authorization* (accessing an API), OIDC provides *authentication* (verifying who the user is). OIDC introduces the **ID Token**, a JSON Web Token (JWT) that contains claims about the authenticated user.

### 3. Authorization Code Flow
This lab implements the Authorization Code flow, the most secure and recommended flow for web applications. 
1. The client redirects the user to the Authorization Server (`/authorize`).
2. The user logs in and grants permission.
3. The Authorization Server redirects the user back to the client (`/callback`) with a single-use **Authorization Code**.
4. The client exchanges this code for tokens at the `/token` endpoint.

### 4. PKCE (Proof Key for Code Exchange)
PKCE is a security extension to OAuth 2.0 for public clients (like Single Page Apps and Mobile Apps). Because public clients cannot safely store a client secret, an attacker who intercepts the Authorization Code could exchange it for tokens. 
PKCE solves this by generating a random `code_verifier` and its hash `code_challenge` (S256). The challenge is sent in the initial request, and the verifier is sent during the token exchange. The server verifies they match, ensuring the same client who started the flow is finishing it.

### 5. State Parameter
The `state` parameter is a cryptographically random string generated by the frontend. It is sent in the `/authorize` request and returned exactly as-is in the `/callback`. The frontend verifies the `state` to prevent Cross-Site Request Forgery (CSRF) attacks.

### 6. ID Token
The ID Token represents **"Who authenticated?"**. It contains claims like the user's name and email, the issuer (`iss`), the intended audience (`aud`), and expiration time. It should be consumed by the frontend to display the user's profile and should **NOT** be used as an API access token.

### 7. Access Token
The Access Token represents **"What can this client do?"**. It is used to access protected resources (like the `/userinfo` endpoint). In this lab, it's implemented as a JWT, but it could also be an opaque string.

### 8. Refresh Token
Refresh tokens allow clients to obtain new access tokens without requiring the user to log in again once the access token expires. They are long-lived and securely stored.

### 9. IAM SSO Session
Single Sign-On (SSO) allows a user to log in once to the Central IAM and seamlessly access multiple applications. 
The IAM server sets an `HTTPOnly` cookie (`iam_session`) on `localhost:3000`. 
- **Frontend 1** and **Frontend 2** do NOT have access to this cookie.
- When Frontend 2 redirects to IAM, the browser automatically sends the `iam_session` cookie to port `3000`. IAM sees the active session and issues a new authorization code for Frontend 2 without asking the user for their password again.

### 10. Tenant Session
This lab simulates "Tenant Sessions". Frontend 1 is "Tenant 1" and Frontend 2 is "Tenant 2". 
Tenant 1 has a policy of `maxSessions: 1` with `REJECT_NEW`. If you try to open a second Frontend 1 session (e.g., in incognito after authenticating the first one), it will be rejected.
Tenant 2 has a policy of `maxSessions: 2` with `REVOKE_OLDEST`. 

### 11. Why frontend does not receive username/password
If the React application handled the username/password directly, it would have access to the user's root credentials, which breaks the security model of OAuth. By redirecting to the central IAM page, the frontend only ever receives temporary, scope-limited tokens.

### 12. Why tokens are not returned in the redirect URL
Returning tokens in the URL (the Implicit Flow) is deprecated because URLs are often logged in browser history, proxy servers, and referer headers. The Authorization Code Flow returns a short-lived code instead, which is then exchanged via a secure POST request.

### 13. Why authorization code is one-time
If an attacker intercepts an authorization code, they might try to use it. Making it single-use ensures that if a legitimate client and an attacker both try to use it, the second attempt will fail (and ideally, the server should revoke tokens from the first attempt if a replay is detected).

### 14. Why PKCE is still required
Even though the authorization code is single-use, an attacker on the same device might register a malicious app to intercept the redirect URI. Because the attacker doesn't know the original `code_verifier` stored in the legitimate app's local storage, they cannot exchange the intercepted code for tokens.

### 15. How SSO works between frontend-1 and frontend-2
Because both apps redirect to `http://localhost:3000` for authentication, they rely on the same global `iam_session` cookie owned by the IAM server. When Frontend 2 redirects the user to `/authorize`, the IAM server reads its own cookie, validates the existing session, and seamlessly redirects the user back to Frontend 2 with a new authorization code, bypassing the login screen entirely.

## The Flow

### First Login (Frontend 1)

Browser
  ↓ (Clicks Login)
Frontend 1
  ↓ (Redirects to /authorize with PKCE challenge & state)
IAM /authorize
  ↓ (No session, redirects to /login)
IAM login page
  ↓ (User enters demo/password123)
IAM SSO cookie created
  ↓
Authorization Code generated
  ↓ (Redirects back)
Frontend 1 /callback
  ↓ (Verifies state, sends code + PKCE verifier to /token)
IAM /token
  ↓ (Verifies code and PKCE, issues tokens)
Frontend 1 receives tokens (Access, ID, Refresh)

### Second Application (Frontend 2)

Browser
  ↓ (Clicks Login)
Frontend 2
  ↓ (Redirects to /authorize with PKCE challenge & state)
IAM /authorize
  ↓ (Reads existing iam_session cookie)
IAM sees existing SSO cookie
  ↓
No login required
  ↓
Authorization Code generated for Frontend 2
  ↓ (Redirects back)
Frontend 2 /callback
  ↓ (Verifies state, sends code + PKCE verifier to /token)
IAM /token
  ↓
Frontend 2 receives its own tokens

## Logout Mechanics
- **Local Logout**: Clears the tokens from the React app's `sessionStorage`.
- **Global Logout**: Redirects to IAM's `/logout` endpoint, which destroys the `iam_session` cookie, ending the SSO session for all applications.

## Known Limitations (Educational Purpose)
- In-memory storage is used instead of a persistent database. Restarting the server resets all users, clients, sessions, and tokens.
- Access tokens and ID Tokens use a single hardcoded RSA key pair generated at startup.
- The IAM `iam_session` cookie is currently not flagged `Secure` because it runs on local HTTP. In production, this MUST be `Secure`.
- Refresh token rotation is omitted for simplicity.
